## Step 1 — Grounding (pre-pinned; restated understanding)

- **(a) For** — This skill exists to create, configure, and debug Claude Code hooks: the fleet's *deterministic* enforcement layer, as opposed to skills/subagents which rely on model judgment. Its consumers are sessions doing security enforcement and quality automation against the real substrate: 15 hook scripts in `.claude/hooks/`, registered through `.claude/settings.json`. CLAUDE.md's non-negotiable rules #3 and #4 ("Hooks enforce; subagents judge", "Exit code 2 to deny") lean directly on this skill being right.
- **(b) Feeds** — A weaker model following this skill writes *real* enforcement artifacts: executable `.claude/hooks/*` scripts, their registration blocks in `.claude/settings.json`, and code that honors the exit-code contract (0/1/2) and the stdin JSON payload shape. The receiving formats are unforgiving: Claude Code's settings schema, its per-event JSON payloads, and its per-event blocking semantics.
- **(c) Disappoints** — The failure class that matters is the hook that *looks* configured but doesn't actually block: a bypassable "firewall," a script on disk that's registered nowhere, a matcher or event that doesn't fire the way the skill claims. The owner trusts "enforced" and it isn't — the worst possible failure for a security layer, because it fails silent and fails safe-*looking*.
- **(d) Wow** — Every enforcement claim in the skill is verifiably true against this repo's real hooks and settings.json and against current Claude Code behavior; following the skill produces hooks that *provably* block (verified, not assumed); and the skill actively flags false-sense-of-safety patterns instead of teaching them.

Since these were pre-pinned, I proceeded directly to the scans. The scans were run against the skill text, its `references/hook-events.md`, all 15 scripts in `/Users/seanwinslow/Code-Brain/code-brain/.claude/hooks/`, `/Users/seanwinslow/Code-Brain/code-brain/.claude/settings.json` and `settings.local.json`, and the live upstream hooks reference/guide (code.claude.com/docs/en/hooks and /hooks-guide) for every capability claim.

**Headline of the evidence pass, because it frames every severity call below:** this repo's deterministic enforcement layer is largely inert *today*, in exactly the ways the skill has no machinery to catch. Both registered PreToolUse "blocking" hooks (`block-secrets.py`, `require-confirm-highrisk.sh`) are no-ops — they read Cursor-era payload keys (`tool`, `target`, lowercase tool names like `bash`/`run_terminal_cmd`) that Claude Code never sends (`tool_name`, `tool_input.file_path`, `Bash`), so every invocation exits 0 and allows. Five of the fifteen scripts are registered nowhere in project settings (`cost-watchdog.py`, `loop-detector.py`, `network-access-control.sh`, `vault-integrity.py`, `daily-note-appender.sh`; three of those aren't even executable). The `permissions` block in settings.json uses an invented schema (`default`/`rules`/`pattern`) rather than the real `allow`/`deny`/`ask` arrays, so the `.env` deny layer is also likely inert. And all ten registrations use relative paths with a `"timeout": 5000` that means 83 minutes, not 5 seconds (upstream `timeout` is in seconds). A skill whose purpose is "hooks that enforce" — sitting in the same `.claude/` directory as this — is the tool that should have made this state impossible.

## Artifact 1 — Seam Report

- `dangerously-wrong` — **Example 1 ("Block secrets access") teaches a bypassable block as a complete solution.** The user asks to "prevent Claude from reading .env files"; the skill answers with a `Read|Edit|Write`-matched PreToolUse hook and declares done. `Bash` (`cat .env`), `Grep`, and any MCP filesystem tool read the same file without ever hitting that matcher — and the skill never says so, never adds Bash to the matcher, and never points at the permission system's deny rules, which upstream docs name as the correct tool for hard file-access denial. Concrete failure the owner observes: he believes `.env` is protected, screenshots the hook, and the very next `cat .env 2>/dev/null` in a Bash call sails through. The live mirror in this repo is worse: the actual registered `block-secrets.py` doesn't even block Write/Edit (dead payload keys, lines 74–80), and the settings.json permissions block that was supposed to cover reads is wrong-schema. Three layers of ".env is protected," zero of them real.
- `dangerously-wrong` — **The "Security Firewall (Bash)" pattern (Complete Hook Script Patterns section) teaches a substring blocklist as a security boundary with no bypassability caveat.** `[[ "$CMD" == *"rm -rf"* ]]` is defeated by `rm -fr`, `rm -r -f`, `command rm`, `/usr/bin/curl`, `cu''rl`, base64-piped payloads, or a `$IFS` split. The skill presents this as the security-firewall reference and moves on. Upstream explicitly warns that the parser-based `if` filter is best-effort and that *the permission system, not a hook, must enforce a hard allow/deny* — this skill inverts that guidance by presenting the hook as the enforcement mechanism. Concrete failure: owner ships the "firewall," runs a red-team command with any trivial obfuscation, and it executes with the hook reporting success.
- `dangerously-wrong` — **Exit-code contract is taught as "exit 1 = error, logged but proceeds" without the loud warning that 1 does NOT block.** The Exit Code Protocol table (lines 68–75) is technically correct but frames 1 neutrally. A weaker model writing an enforcement hook that hits a real internal failure (jq missing, malformed JSON) will very reasonably `sys.exit(1)` on error — and the action it was guarding *proceeds*. Upstream flags this exact trap with a standing Warning ("If your hook is meant to enforce a policy, use exit 2 ... Claude Code treats exit code 1 as a non-blocking error and proceeds"). The skill has the data but not the danger flag. Concrete failure: a security hook that errors out (rather than deciding) silently fails open, and the owner reads the exit-1 line as "it errored safely."
- `dangerously-wrong` — **No verification step exists, so a weaker model cannot tell a firing hook from a dead one — the exact (c) disappointment, unguarded.** The skill's entire lifecycle is "write script → add JSON → done." Nothing instructs the implementer to confirm the payload keys match what Claude Code actually sends, to test that exit 2 blocks, or to check the hook is registered and firing. This is precisely how this repo arrived at two registered no-op firewalls and five orphaned scripts: `block-secrets.py` (line 74) reads `hook_data.get('tool')` and `is_blocked` off `target`/`file_path`, while Claude Code sends `tool_name` and `tool_input.file_path` (confirmed against `references/hook-events.md` lines 22–61 and live docs) — so it always exits 0. `require-confirm-highrisk.sh` (lines 9, 13) matches `run_terminal_cmd`/`bash` and greps a flat `"command"` key; Claude Code sends `Bash` and nests the command under `tool_input`. Both are dead, both are registered as the project's PreToolUse security layer, and a skill named "hooks-configuration and *debugging*" ships no move that would surface it.
- `structural` — **The stdin payload schema the skill teaches is under-specified and never cross-checks the flat-vs-nested shape that breaks real hooks.** Example 1 reads `data.get('tool_input', {}).get('file_path', '')` (correct); the Secret Blocker pattern repeats it (correct); but nothing in the skill body states the canonical schema as a contract — that `tool_name` is top-level, `tool_input` is a nested object, and the field names are exact. The reference file has the right examples but the SKILL.md never forces the implementer to it, and the repo's own scripts fetch `tool`/`target`/`command` from the top level. A weaker model extending an existing repo hook will pattern-match the *broken local scripts* over the skill's correct-but-unemphasized examples. Concrete failure: new hook reads the wrong keys, exits 0 on everything, joins the dead-firewall pile.
- `structural` — **No adapter between "script on disk" and "registered in settings.json" — orphaned scripts are invisible to the skill.** The skill's Configuration Best Practices (lines 241–248) cover scope (global vs project) but never say "a hook does nothing until it is registered in the `hooks` block of a settings file, and a script in `.claude/hooks/` that isn't referenced there never runs." Five scripts in this repo prove the gap: `cost-watchdog.py`, `loop-detector.py`, `network-access-control.sh`, `vault-integrity.py`, `daily-note-appender.sh` exist and are absent from both `settings.json` and `settings.local.json`. Three (`cost-watchdog.py`, `loop-detector.py`, `vault-integrity.py`) also lack the executable bit. Concrete failure: owner writes a cost watchdog, drops it in `.claude/hooks/`, assumes budget is enforced; it has never executed once.
- `structural` — **`timeout` unit is never stated, and the repo already has it wrong.** The reference table (line 113) lists `timeout` defaults but not the unit; SKILL.md's command-hook example uses `"timeout": 30` with no unit gloss. settings.json registers both SessionStart hooks with `"timeout": 5000` — intended as 5s, but upstream `timeout` is **seconds**, so this is 83 minutes. Because SessionStart can't block, the practical effect is a session-start context injector that can hang far past intent. Concrete failure: owner copies `5000` as a "5 second" idiom into a blocking Stop/PreToolUse hook and gets a session that appears frozen for over an hour on a stuck check.
- `structural` — **Adapter gap: the skill teaches only `command` / `prompt` / `agent`, but the live platform has `http` and `mcp_tool` types and a materially larger event set.** The Hook Event Reference table (lines 56–65) lists 8 events; the live platform documents ~20+ (including `PermissionRequest`, `PostToolUseFailure`, `SubagentStart`, `PostCompact`, `SessionEnd` reasons like `bypass_permissions_disabled`, `FileChanged`, `StopFailure`, `ConfigChange`, etc.) and 5 hook types. More consequentially, the skill omits `PreToolUse`'s **JSON `permissionDecision` output** (`allow`/`deny`/`ask`/`defer` via `hookSpecificOutput`) — the modern, structured way to deny a tool call with a reason surfaced to the user, distinct from raw exit 2. Concrete failure: owner asks "deny this tool and tell the user why," the skill only knows exit-2-to-stderr (fed to Claude, not cleanly to the user), and the richer, intended mechanism is never offered. The skill isn't wrong about what it covers; it's silently a version or two behind the surface it configures.
- `structural` — **`references/hook-events.md` and the settings.local.json interaction with the `permissions` block are never connected, so the skill can't diagnose the repo's inert `.env` deny.** settings.json carries a `permissions` block with `"default": "ask"` and `rules: [{pattern, permission}]` — an invented schema; the real Claude Code shape is `permissions: { allow: [], deny: [], ask: [] }` with `Read(./.env)`-style entries. The skill scopes itself to hooks and explicitly disclaims permissions/CLAUDE.md, which is defensible — but since it *does* teach ".env blocking" as a flagship example and the correct answer for file-read denial is a permission deny rule, the skill needs at least a pointer ("hard file-access denial belongs in the permissions `deny` array, not a hook matcher"). Concrete failure: the owner's `.env` protection lives half in a dead hook and half in a malformed permissions block, and the hooks skill — the one he'd consult — has no hook-adjacent note that would catch either.
- `minor` — **The Auto-Format pattern uses `path.rsplit('.', 1)[-1]` and `FORMATTERS['.py'] = ['ruff', 'format']`.** `ruff format` is correct but the real repo hook (`format-on-edit.sh`) uses `black` for Python and `prettier` for JS/TS with `command -v` guards — the skill's inline pattern has no "is the formatter installed" guard, so on a machine without `ruff` it exits 1 (non-blocking, fine) but prints a scary "Format failed" to stderr on every edit. Concrete failure: noise, not breakage.
- `minor` — **Matcher reference omits that `Stop`/`UserPromptSubmit` "always fires" is a small subset of the no-matcher events, and doesn't mention `,` as an alternation separator alongside `|`.** Live docs accept both `|` and `,` for most events. Low stakes, but a weaker model may write `"Edit,Write"` and not know whether it's valid (it is, for these events).
- `minor` — **`run-tests-on-stop.sh` in the repo is non-blocking (backgrounds tests with `&`, always exits 0), but the skill's Example 3 and Stop-gate pattern teach a *blocking* exit-2 test gate.** Not a skill defect per se, but the skill's own success criterion "Exit code 2 blocks the intended action" is contradicted by the flagship Stop-hook the repo actually ships — worth a note that a backgrounded test runner is fire-and-forget telemetry, not a gate, so the reader doesn't conflate the two.

## Artifact 2 — Intent-Carrying Improvement Spec

### Objective

The skill is the fleet's authority on the *deterministic* enforcement layer — the thing that's supposed to be trustworthy precisely because it doesn't depend on model judgment (CLAUDE.md rules #3, #4). Its most demanding consumer is a weaker model writing real `.claude/hooks/*` scripts + `settings.json` registrations that security and quality actually ride on. Today the skill teaches hooks that *look* enforced but don't block (bypassable matchers, substring blocklists, exit-1 fail-open), teaches the stdin payload shape loosely enough that a weaker model reproduces the repo's dead-key bugs, and ships **no verification move** — so it cannot catch, and actively reproduces, the exact failure this repo is already living in: two registered no-op firewalls, five orphaned scripts, a mis-unit timeout, and a wrong-schema permissions block. For a security skill, "works in the demo, silently fails in prod" is the whole disappointment (c), and it's unguarded.

### Desired outcome

A weaker model following the revised skill produces hooks it can *prove* block — every enforcement example either uses exit 2 correctly or hands off to the permission system, and every one carries an explicit bypass caveat where a bypass exists. The implementer always cross-checks the real Claude Code stdin schema (`tool_name` top-level, `tool_input.*` nested, exact tool names like `Bash`) before trusting a hook, always confirms the script is registered and firing, and understands that exit 1 fails *open*. When the owner asks "is `.env` protected?", the skill's answer routes hard file-access denial to the permission `deny` array and only uses hooks for what hooks can actually guarantee. The wow bar from (d): every enforcement claim is verifiable against this repo's real hooks + settings, and the skill flags false-sense-of-safety patterns instead of teaching them. Net observable difference: the owner stops discovering, weeks later, that a hook he screenshotted as "enforced" was inert.

### The fix, per finding

**Fix — Example 1 bypassable block taught as complete (dangerously-wrong).** Rewrite Example 1 so the *first* thing it says is that a PreToolUse matcher only covers the tools it names — `Read|Edit|Write` does not stop `Bash cat .env`, `Grep`, or MCP file tools — and that **hard file-access denial belongs in the `permissions.deny` array** (`Read(./.env)`, `Read(./secrets/**)`), with the hook as defense-in-depth, not the primary boundary. If the example keeps the hook, its matcher must include `Bash` and the example must note that even then, command obfuscation can evade it. Reasoning a weaker model must carry: a hook matcher is a *filter on named tools*, not a filter on *file access*; the same file is reachable through tools your matcher doesn't list, so a hook can never be a complete file-access boundary by itself. The moment the edge case is "but what about `cat`/`grep`/an MCP tool," the answer is "that's why the permission system, not the matcher, owns denial." Do not let this example end on "done" — it must end on "verify the block by attempting the read through Bash."

**Fix — Security Firewall substring blocklist (dangerously-wrong).** Add a bold caveat directly under the pattern: a substring/regex blocklist is a *speed bump, not a boundary* — `rm -fr`, `rm -r -f`, quoting, `$IFS`, absolute paths, and base64 piping all defeat it — and per Claude Code's own guidance, a hard allow/deny must be enforced through the permission system, with the hook as a secondary layer. Keep the pattern (it's a fine speed bump) but reframe its role. Reasoning to preserve: any denylist you can enumerate, an adversarial string can escape; enforcement you actually trust must be allowlist-shaped or live in the permission layer. A weaker model hitting "should I add `rm -fr` to the blocklist too?" needs to understand the answer is "you'll never finish that list — change the mechanism, don't extend the list."

**Fix — exit 1 fails open (dangerously-wrong).** Promote the exit-code semantics from a neutral table row to an explicit, bolded rule: **exit 1 does NOT block — the guarded action proceeds. An enforcement hook must exit 2 to deny, and must exit 2 (not 1) on its own internal errors if failing safe means blocking.** Add one line on the fail-open vs fail-closed decision: for a security gate, decide deliberately whether an internal error should block (exit 2) or allow (exit 0/1), and never let it be an accident. Reasoning a weaker model needs: 1 is the Unix "I failed" convention, so the instinct is to exit 1 on error — but Claude Code reads 1 as "non-blocking, proceed," so an enforcement hook that exits 1 on a jq/parse failure silently lets the dangerous action through. On any edge case where the hook can't decide, the safe default for a *security* hook is exit 2 with a stderr reason.

**Fix — no verification step / dead-key bugs (dangerously-wrong, and the core of disappointment (c)).** Add a mandatory final section, "Verify the hook actually fires and blocks," as a hard step before the skill considers any enforcement hook done. It must instruct: (1) confirm the script reads the **real** Claude Code stdin schema — `tool_name` at top level, `tool_input` as a nested object, exact PascalCase tool names (`Bash`, `Edit`, `Write`, `Read`), never `tool`/`target`/`command`/`bash`/`run_terminal_cmd` (those are a different tool's schema and always evaluate to empty → exit 0 → allow-everything); (2) confirm the hook is registered in a settings file's `hooks` block (a script in `.claude/hooks/` that nothing references never runs); (3) actually exercise it — echo a representative payload into the script and assert exit 2, e.g. `echo '{"tool_name":"Bash","tool_input":{"command":"rm -rf /"}}' | .claude/hooks/firewall.sh; echo "exit=$?"` must print `exit=2`; (4) name `/hooks` (read-only menu of what's actually registered and from which settings file) and `claude --debug-file` / `/debug` as the tools to confirm firing and see matched hooks + exit codes. Reasoning to carry: a hook that reads the wrong payload keys is indistinguishable from a working hook *until an attack slips through*, because it exits 0 (allow) on every input including the ones it was written to catch; the only way to know it works is to feed it a should-be-blocked payload and watch for exit 2. This single section is the highest-leverage fix in the audit — it's the move that converts "looks configured" into "provably blocks," and it's the direct antidote to the two dead firewalls and five orphaned scripts already in this repo.

**Fix — under-specified stdin schema contract (structural).** Add a short "Canonical stdin payload (read this exactly)" block to the SKILL body (not only the reference file), stating the exact shape for the common events with the top-level-vs-nested distinction called out, and a one-liner: "If you're extending an existing hook in a repo, do not trust its key names — verify them against this schema; Cursor/other-tool hooks use `tool`/`target` and will silently fail under Claude Code." Reasoning: a weaker model extending a repo will imitate the nearest existing script, and in this repo the nearest scripts are wrong; the skill must make the correct schema more authoritative than the local precedent.

**Fix — script-vs-registration adapter gap (structural).** In Configuration Best Practices, add: "A hook does nothing until it is registered in the `hooks` block of a settings file *and* (for command hooks) the script is executable (`chmod +x`). Writing a script into `.claude/hooks/` does not activate it." Have the new verification section cross-check both. Reasoning: registration is the adapter between "code exists" and "code runs"; without naming it, a weaker model treats file creation as completion — which is how five scripts here became orphans, three of them non-executable.

**Fix — timeout unit (structural).** State the unit explicitly wherever `timeout` appears: "`timeout` is in **seconds** (default 600 for command/http/mcp, 30 for prompt and for UserPromptSubmit). `"timeout": 5000` is 83 minutes, not 5 seconds." Add a caution that an over-large timeout on a blocking hook can appear to freeze the session. Reasoning: the repo already encodes the 5000-as-5s mistake; the skill must inoculate against copying it into a blocking hook where the stall is user-visible.

**Fix — missing hook types/events and `permissionDecision` output (structural).** Add `http` and `mcp_tool` to the hook-types list (one line each) and add a short "Deny with a structured decision" note: PreToolUse can emit JSON on stdout (exit 0) with `hookSpecificOutput.permissionDecision: "deny"` + `permissionDecisionReason`, which surfaces a clean reason and is the modern alternative to raw exit-2-to-stderr. Flag the event table as a curated subset and point to the live reference for the full set (PermissionRequest, PostToolUseFailure, SubagentStart/Stop, etc.). Reasoning: the skill configures a moving platform; it should teach the structured deny path (cleaner UX, distinct from Claude-facing stderr) and admit its event list is a subset so a weaker model knows to check upstream rather than conclude an event doesn't exist.

**Fix — permissions-block pointer (structural).** Add one hook-adjacent line to the `.env` example and Best Practices: "Hard file-access denial (`.env`, `secrets/`) is enforced by the `permissions.deny` array in settings.json using tool-scoped patterns like `Read(./.env)` — not by a `permission`/`rules`/`pattern` schema (that shape is ignored) and not by a hook matcher alone." Reasoning: the repo's permissions block is invented-schema and inert; the skill's flagship example is exactly the topic that should catch it, so a pointer here closes the loop without expanding the skill's scope into a full permissions tutorial.

**Minor fixes (listed, no full reasoning):** (1) Add `command -v <formatter>` guards to the Auto-Format pattern and note `ruff`/`black`/`prettier` must be installed. (2) Note `,` works alongside `|` as a matcher separator for events that support matchers. (3) Add a one-line contrast that a backgrounded test runner (`npm test &; exit 0`) is fire-and-forget telemetry, not a gate — a real Stop gate must run tests synchronously and exit 2 on failure — so the reader doesn't mistake the repo's non-blocking `run-tests-on-stop.sh` for enforcement.

### What NOT to change

- **The exit-code table's values (0/1/2) are correct** — keep them; only add the fail-open emphasis, don't restate the semantics.
- **The `{"ok": true/false, "reason": ...}` schema for prompt/agent hooks is correct** — verified against live docs (prompt and agent hooks share that response format; agent hooks get a longer default timeout and up to 50 tool turns). Do not "fix" it.
- **The `stop_hook_active` loop-prevention guidance for Stop hooks is correct and load-bearing** — keep it; it's real and matches upstream.
- **The `references/hook-events.md` payload examples are accurate** (`tool_name` top-level, `tool_input` nested) — the fix is to make the SKILL body point at them harder, not to rewrite them.
- **The skill's scoping disclaimer** (not for prose critique / not for CLAUDE.md auditing) is fine — do not expand the skill into a general permissions or settings tutorial; the permissions fixes are pointers only.
- **The overall shape** (Purpose → When to Use → event table → exit codes → hook types → patterns → matcher/async → best practices → success criteria) is sound and readable — this is an additive hardening pass (add caveats + a verification gate + schema authority), not a restructure.
