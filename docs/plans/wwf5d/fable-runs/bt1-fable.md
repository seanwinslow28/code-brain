# Artifact 2 — Intent-Carrying Improvement Spec

For the implementing model: this spec carries the reasoning on purpose. When you hit a case it doesn't spell out, decide from the Objective and the per-fix reasoning, not from the literal diff.

## Objective

intent-engineering is the carry-the-why backbone of Sean's agent fleet (grounding (a)): skill-audit's and zoom-out-and-think's Step-5 specs are built on its scaffolding, every agent build uses its template and autonomy levels, and a shipped, npm-published MCP server (`sw-mcp-intent-engineering`) implements its checklist as code and names this SKILL.md canonical (grounding (b)). Today it under-delivers in three owner-felt ways (grounding (c)): the full template is heavyweight for small jobs, the retrofit levels have no reproducible selection rule, and the validation checklist is advisory — in a skill whose central thesis is that constraints that matter must not be advisory. The problem to solve: make the skill's own quality machinery **self-enforcing, right-sized, and handoff-proof**, so its specs survive Fable → Opus → subagent with zero intent drift (grounding (d)). When facing trade-offs, prioritize **enforceability and traceability over new teaching content** — the teaching content is already strong (see What NOT to Change), and every fix below is additive because the section/checklist text is mirrored in shipped code.

## Desired Outcome

Observable differences from the owner's chair, mapped to (c) and (d) — not "section X now says Y":

1. **An unvalidated spec is visually distinguishable from a validated one.** Every spec, review, or retrofit the skill emits ends with a validation-verdict block (per-group results; every failing item either fixed or explicitly waived with a one-line reason) — or the pasted output of `audit_intent_spec`. "Nothing forces it to run" stops being true because a spec without the block is visibly unfinished.
2. **Every output opens with a declared profile line** ("Level 1 (floor) because ..." / "Full 9-section because ...") chosen by a written decision rule, so "when is Level 1 enough?" has the same answer on any two runs, by any model.
3. **A Level-1 retrofit can pass validation.** The checklist is scoped to the declared level, so checklist failures are signal again instead of by-design noise on 13 of 25 items.
4. **Escalation stops losing protections.** Improvement specs that step up from the consumers' 4-element floor to the full template still carry What-NOT-to-change; scheduled-agent retrofits carry the canonical Zero-Interaction Mandate text, copied not paraphrased.
5. **The next checklist edit lands in both places.** The skill text itself says the checklist/anti-patterns are mirrored 1:1 in `sw-mcp-intent-engineering`, so no editor forks them unknowingly.

## The Fix, Per Finding

Every `dangerously-wrong` and `structural` finding is carried forward with reasoning; `minor` findings are listed at the end without full writeups.

### F1 — Give the Validation Checklist gate semantics (fixes the `dangerously-wrong` finding)

**Change:** Add a short "How to run this checklist" preamble to the Validation Checklist section defining three things: (a) **output** — running the checklist produces a per-group verdict block appended to the emitted spec (group → pass / fail / waived, with failing items named); (b) **failure semantics** — each failing item is either fixed before the spec is emitted, or listed as `WAIVED: <one-line reason>`; silence is the only forbidden state; (c) **routing** — if the intent-engineering MCP tools are available in the session, run `audit_intent_spec` on the draft and paste its score + findings as the verdict block; hand-run only when the tools are absent. Amend all three "Run the Validation Checklist" bullets in "How to Use" to "...and append the verdict block — do not emit a spec without it."

**Reasoning to carry:** The skill's own Key Architectural Insight is that constraints that matter can't live as prompt suggestions. The verdict block is the nearest thing a SKILL.md has to architectural enforcement: it makes an unvalidated spec *detectably different* from a validated one, which is what turns "please validate" into a gate. The point is not paperwork — if you find yourself generating a verdict block without actually evaluating items, you have recreated the original failure one level down. **Edge guidance:** if the artifact under review is a fragment (one section being discussed), the verdict block may cover only the touched groups but must say so explicitly. If the user explicitly declines validation, emit the spec with a `VALIDATION: SKIPPED (user request)` line — the visible mark is the non-negotiable part, not the ceremony.

### F2 — Scope the checklist by retrofit level (fixes the level-blind-checklist seam)

**Change:** Tag each of the seven checklist groups with the levels it applies to: L1 = Objective Quality + Outcome Quality + Stop Rule Quality; L2 adds Health Metric + Constraint + Autonomy + Edge Case Quality; L3/full spec = all 25 items. Retrofit step 4 becomes "Run the checklist subset for the level you declared in step 2." The verdict block (F1) records which subset ran.

**Reasoning to carry:** A gate that is guaranteed to fail 13 of 25 items on every honest Level-1 run trains the operator to ignore the gate — scoping is what makes F1 honest rather than theater. The declared level (F5) is the key the subset selection hangs off, which is why the level must be stated in the output, not just decided in the model's head. **Edge guidance:** scope by *content present*, floor by *declared level* — if an L1 retrofit voluntarily includes an Edge Cases section, validate that section too; never validate below the declared level.

### F3 — Canonicalize the Zero-Interaction Mandate (fixes the mandate seam)

**Change:** Add a small named subsection near MVR Level 1 containing the mandate's canonical, copy-pasteable text: never ask clarifying questions or prompt for input; the *why* (runs unattended via launchd — no human is available, and any prompt for input causes a silent timeout hang, not a visible error); the fallback (if the agent cannot proceed, write an error note at the agent's designated error anchor and halt). Instruct: copy this block into the Stop Rules and adapt only schedule/anchor specifics — never re-derive it from an example. Update the checklist item wording from "Zero-Interaction Mandate is present" to "present **with the halt-and-error-note fallback**" — and because that item is mirrored as `stop.zero-interaction-mandate` in the MCP server, make this wording change **paired** with an MCP-side update per F5's sync rule.

**Reasoning to carry:** This is the one input in the skill where a paraphrase can strand a production agent: a mandate that says "don't ask questions" but omits the halt-and-error-note half leaves the agent with no defined behavior at exactly the moment it's stuck at 3 AM.
