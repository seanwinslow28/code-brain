# Wince Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `wince`, a user-invoked skill that shows a person options, reads which ones they wince at, and emits a reusable taste block that makes an image model draw like them.

**Architecture:** A prompt artifact, not a program. `SKILL.md` carries the four-stage interview engine (Widen, Fork, Push, Negate) and the emit rule; `references/` carries the block schema, the copy-paste tier, the worked proof, and the example blocks. The library is plain markdown files on disk. Nothing calls an API directly; the skill drives whatever image generation the host session already has.

**Tech Stack:** Markdown + YAML frontmatter. Verification is `python3 scripts/validate.py` for mechanics and scripted behavioral gates for the parts a validator cannot see.

**Spec:** [docs/superpowers/specs/2026-08-10-wince-taste-interview-design.md](../specs/2026-08-10-wince-taste-interview-design.md) (approved 2026-08-10).

**A note on TDD in a prose artifact.** There is no pytest here. The failing-test-first discipline still applies and takes two forms: `scripts/validate.py` for anything mechanical, and a written pass criterion checked against real output for anything behavioral. Every behavioral task below states its criterion *before* the content that satisfies it. A gate you can only evaluate after seeing the output is not a gate.

### Task 2: The block schema

**Files:**
- Create: `.claude/skills/wince/references/block-schema.md`

- [ ] **Step 1: Write the pass criterion**

Record it at the top of the file as a comment the implementer must satisfy:

> A stranger who has never heard of Wince can paste a filled block into a fresh ChatGPT or Claude window with a one-line scene request and get back something in their style. No JSON, no tool-specific syntax, no reference to Wince anywhere in the block body.

- [ ] **Step 2: Write the schema file**

`.claude/skills/wince/references/block-schema.md` contains, verbatim, the template below plus one paragraph per field explaining what a good answer looks like and one showing a weak answer for contrast.

```
# TASTE BLOCK — <name>
version: <n> · <date>

## INTENT
1. CORE THESIS       what the thing should feel like before it announces itself
2. EMOTIONAL MODE    what it favors, and what it favors it OVER
3. STRUCTURE         the focal discipline; what gets room, what gets cut
4. NARRATIVE STANCE  how the meaning reaches the audience

## EXECUTION (visual)
5. MEDIUM / SUBSTRATE   what it's made of and made on
6. THE HAND             how the marks get made
7. COLOR / LIGHT        the palette discipline, stated as a constraint
8. THE FINISH           how finished it should look, and how finished it must NOT look
9. THE ONE MOVE         the single decision that carries the meaning

## NEVER DO
   the ban list; every item carries its why
```

One worked field, showing the pattern every other field entry must follow:

> **8. THE FINISH** — how finished it should look, and how finished it must NOT look.
>
> *Strong:* "Unfinished on purpose. Construction lines stay in, the searching marks stay in, the paper grain stays visible. It should look like it was caught mid-decision, not delivered."
> *Weak:* "Hand-drawn style." That names a category, not a boundary, and the model will resolve the ambiguity toward its own average every time.
> *Also strong, opposite direction:* "Immaculate. No visible tooling, no grain, no brushwork. Any evidence of process is a defect."
>
> The field is doing its job when a stranger reading the answer could reject a candidate image with it.

Two hard rules stated in the file:

- **EMOTIONAL MODE must name what it favors things OVER.** "Quiet and patient" is half an answer. "Quiet tension over spectacle, patience over instant payoff" is a usable one, because it tells the model what to sacrifice.
- **Every NEVER DO item carries its why, and the why is the negative of a value the keeps demonstrated.** A ban without a reason is a preference; a ban with one is a rule the model can extend to cases nobody listed.

- [ ] **Step 3: Verify against the two real blocks**

Run: `cat vault/20_projects/substack-studio/rung-0-taste-experiment/capture/taste-blocks/sean-intent-layer.md`

Then check the execution block in `vault/20_projects/substack-studio/rung-0-taste-experiment/capture/prompts.md` (Thread B, round 05) maps onto EXECUTION 5-9 with nothing orphaned. If a field in either real block has no home, the schema is wrong, not the block.

### Task 3: The dig-to-the-decision rule

**Files:**
- Modify: `.claude/skills/wince/SKILL.md`

- [ ] **Step 1: Write the pass criterion**

> Given a user answer of "I like that one, the texture is nice," the skill asks again rather than recording it. It stops asking only when the answer would still be actionable applied to a subject the user never mentioned.

- [ ] **Step 2: Add the section to SKILL.md**

Add a `## The one rule that makes this work` section containing the surface-vs-decision contrast verbatim from spec §2, plus this instruction:

> Never accept a bare preference. When someone says "I like that one," ask what decision the maker made. Keep going one level down until the answer would still be useful applied to a different subject. Two follow-ups is usually enough; four is an interrogation and people quit. If the third try still lands on surface, record the surface answer, mark it thin, and move on. A thin field is honest. A fabricated one is not.

- [ ] **Step 3: Verify by dry-run**

Run the section against three canned answers and confirm the intended behavior:

| Answer | Expected |
|---|---|
| "I like the texture" | asks again |
| "I want the process visible, the marks are evidence of thought" | records it |
| "I dunno, it just looks cool" x3 | records thin, marks it, moves on |

### Task 4: The four stages

**Files:**
- Modify: `.claude/skills/wince/SKILL.md`

- [ ] **Step 1: Write the pass criterion**

> A full run completes in under ten minutes and spends three or four generations. Widen and Negate spend zero. If a run reaches Emit having never generated an image, the run failed and the skill says so instead of emitting.

- [ ] **Step 2: Write the stage table and per-stage instructions**

Add `## The four stages`. For each stage, the file gives its job, its generation budget, its exit condition, and the actual language to use.

**Widen** (0 generations). Offer five named directions deliberately far apart, described in one line each, no images. The spread must cross medium, finish, and register, not five flavors of one look. Exit when at least three are dead.

**Fork** (2-3 generations). Take the survivors, generate them against the user's actual subject. Same subject every time, so the delta reads as style and not composition. Pick one, then dig per Task 3. Exit when one direction is chosen with a decision-level reason.

**Push** (1 generation, may reuse Fork's winner). Deliberately overshoot the chosen direction. Tell the user that is what you are doing. Use the framing that worked: go too far on purpose, they will pull it back. Exit when the user has named a ceiling, whether or not they liked the result.

**Negate** (0 generations). Walk back through everything killed in Widen, Fork, and Push and ask why each one was wrong. This is where NEVER DO comes from. Exit at five to ten banned items, each with a why.

Then **Emit** the block per the schema, name it, stamp version 1 and the date.

- [ ] **Step 3: Add the Push justification**

State it in the file so nobody optimizes it away:

> Push is the only stage that finds something the user did not know to ask for. Every other stage narrows what they already brought. Cut it and this becomes an interview about a spec, which is the thing that does not work.

- [ ] **Step 4: Verify the budget arithmetic**

Read the stage table and confirm the generation counts sum to 3-4, matching the criterion in Step 1. If Fork takes 3 and Push takes its own, that is 4 and acceptable. Five is not.

- [ ] **Step 5: Commit**

```bash
git add .claude/skills/wince/SKILL.md
git commit -m "feat(wince): four-stage interview engine with generation budgets"
```

### Task 5: Refusal handling and degraded paths

**Files:**
- Modify: `.claude/skills/wince/SKILL.md`

- [ ] **Step 1: Write the pass criterion**

> When a generation is refused by a content filter, the skill says what happened, re-aims once at something that is not a person, and moves on. It never rewords the same request a third time.

- [ ] **Step 2: Add the section**

Add `## When the model refuses` with the evidence stated plainly, because it is real and it is the skill's own house data:

> Push is the stage most likely to be refused, because "make it ugly, go too far" is exactly the shape safety filters catch. Measured 2026-08-09 on GPT Image 2: enhancement language aimed at an image containing a child was refused 3 of 3 times and again after a reword, while a plain compositional edit on the same image passed. With a described likeness of a real person in the chain, the model refused to make the subject prettier (3 of 3) and refused to make them uglier (2 of 2), while "strip the room out" and "make it look hand drawn" passed untouched. The face is fenced. Everything around it is not.
>
> So: on a refusal, say so out loud, then re-aim the push once at composition, palette, or finish rather than the figure. If that is also refused, skip Push, tell the user the block will be thinner for it, and continue. Do not reword a request until it slips past a filter. That is not a workaround, it is evasion, and the block you would get is not worth it.

- [ ] **Step 3: Add the no-generation degraded path**

> If the session cannot generate images, say so at the start, not at Fork. Run all four stages in words, mark the emitted block `mode: words-only`, and tell the user which fields are least trustworthy as a result (THE HAND and THE FINISH, which are the two nobody can judge from a description).

- [ ] **Step 4: Verify**

Confirm both paths are stated before the stage table refers to them, so a reader hits the rule before the situation.

- [ ] **Step 5: Commit**

```bash
git add .claude/skills/wince/SKILL.md
git commit -m "feat(wince): filter-refusal handling and words-only degraded path"
```

### Task 6: The library

**Files:**
- Modify: `.claude/skills/wince/SKILL.md`
- Create: `.claude/skills/wince/references/library.md`

- [ ] **Step 1: Write the pass criterion**

> Running Wince twice produces two named blocks, not one overwritten one. Running it against an existing block bumps the version and interrogates what changed rather than starting over.

- [ ] **Step 2: Define the operations**

Three, named in `SKILL.md` and detailed in `references/library.md`:

- **new** — the full four-stage run, emits a named block at version 1.
- **list** — read the blocks directory, print names, versions, and one-line thesis each.
- **refine `<name>`** — load an existing block, run Fork and Push only against its current state, ask what has changed, bump the version, keep the old one.

Blocks live in `taste-blocks/` at the root of whatever project the user invokes from, one file per block, named `<slug>.md`. State the location in the file; do not invent a hidden dotfile directory.

- [ ] **Step 3: Add the refine-not-overwrite rule**

> Refine never rewrites a block from scratch. Taste sharpens; it rarely reverses. Load what exists, ask what has changed since, and edit. A refine that produces a completely different block means the user has a second style, not a revised one. Say so and offer to make a new one instead.

- [ ] **Step 4: Verify**

Confirm the three operations are mutually exclusive and that every one names its exit condition.
