Audience: one listener, Sean — a product manager with NO engineering background who runs a 12-agent autonomous AI system in production every day.

CALIBRATION FOR THIS MODULE: this is the module where he already knows the most. He has BUILT, without knowing the names: a cost-aware router with a fail-closed policy (an off-hours miss raises an error rather than silently billing a paid API), a circuit breaker, idempotent retry with typed deferral, a stop-reason taxonomy, a pre-flight budget check that projects month-to-date plus predicted cost and refuses BEFORE the call, hierarchical cost caps, a quality gate that logs its rejection reasons, a grounding gate that drops any claim not traceable to a fetched URL, capability deny-lists on read-only agents, and hard policy gates that run before an action rather than asking nicely in a prompt. NAME these things for him and tell him he already built them — that recognition is the point of the module. Do NOT teach him what an agent, a harness, a model, an API or a router is.

What he has NOT built and must be taught from zero: a tool registry, session persistence and resumability, workflow state as distinct from conversation state, and ANY threat modelling whatsoever. He runs tool-calling agents with filesystem and network access and connected MCP servers and has never asked what an attacker could make them do.

- DO define every term in plain language on first use: workflow vs agent, compounding error, tool registry, trust tiers, defense in depth, idempotency, stop-reason taxonomy, determinism boundary, frozen vs variable, CACE, glue code, pipeline jungle, undeclared consumers, STRIDE, prompt injection, context poisoning, goal hijacking.
- CRITICAL RULE: never mention a company, incident, paper, researcher or tool without a one-sentence setup first explaining what it is and why it is being mentioned. Assume no prior familiarity. This is the single most important instruction.

Cover, in this order:

1. Open on the mirror, and spend real time here. Walk through the specific things he built and name each one. This is the emotional core of the module: he has been doing competent architecture for eighteen months and could not describe it. Be specific and concrete about his own systems rather than generic.
2. The first architecture decision: workflow or agent. Set up the source properly — Anthropic, the company that builds Claude, published an engineering piece called Building Effective Agents. A workflow orchestrates the model through predefined code paths that YOU chose; an agent lets the model direct its own process at runtime. The distinction is not sophistication, it is who chose the sequence. Their recommendation is conservative: workflows beat agents whenever the task structure is stable enough to encode, because a workflow pays inference cost only at decision points you chose. Cover the five patterns — prompt chaining, routing, parallelisation, orchestrator-worker, evaluator-optimiser — and point out that he already built two of them: his router is routing, and his nightly critic over his synthesizer is evaluator-optimiser. Explain compounding error with the arithmetic: 95% reliability per step over ten steps is about 60% end to end.
3. The retrieval fork: retrieval is for knowledge that changes, fine-tuning is for behaviour that should be consistent, long context is for when the problem is small enough that you should stop optimising.
4. The harness and the 80 percent. Set up the anecdote properly: in 2026 Anthropic accidentally published the full source of Claude Code in an npm package that failed to exclude a source map file, and third-party analysis produced the most complete public picture of production agentic infrastructure. The finding: the model call is about 20 percent of the system, the other 80 percent is plumbing. Walk the day-one primitives in build order — tool registry, permission system with trust tiers (the shell tool alone has an eighteen-module security stack, defense in depth), session persistence, workflow state and idempotency, pre-turn budget checks, structured streaming events, system event logging, and a basic invariant test suite. Stress that the invariant suite is the cheap day-one version of what evals become later.
5. The autoCompact anecdote, told carefully: the automatic context-compaction routine retried indefinitely on failure; one session failed 3,272 consecutive times, silently burning tokens; the fix was three lines, a maximum-consecutive-failures constant. Three lines of budget guardrail missing from a product doing billions in revenue. Then the payoff — hold that next to his own pre-flight budget check, which projects and refuses before the call. He got that right and they did not.
6. Workflow state versus conversation state, and idempotency. Conversation state answers what have we said; workflow state answers what step are we in, what side effects already fired, is this safe to retry. Restoring a transcript does not tell you whether the email was already sent. Explain idempotency keys plainly. Note that his deferral design already gets this right and that what he lacks is resumability within a run.
7. The determinism boundary — the most product-manager-specifiable decision in the whole stack. Constraints live in code, not in prompts, because models approximate rather than count. Frozen versus variable regions. And the non-obvious one: validate after every transformation, not just at the end, because a model can draft inside a limit and then violate it during a later tone pass. Give the loop: generate, validate, repair, validate again — and repair with exact numbers rather than try again.
8. Technical debt. Set it up: in 2015 a team at Google led by D. Sculley published a paper called Hidden Technical Debt in Machine Learning Systems, which established these as systems problems rather than modelling problems. Cover CACE — changing anything changes everything — glue code measured at 95 percent or more of a mature codebase, pipeline jungles, and undeclared consumers. Then the 2026 extension: agentic debt is a stock, the stochastic tax is a flow, the ongoing burden a probabilistic system imposes even when nothing is broken. Note it is a fresh preprint and date it.
9. Security — and say plainly that this is the one section with no mirror, the part of his own fleet he has never examined. Set up Microsoft's AI Red Team taxonomy, updated in 2026 on twelve months of red-teaming deployed systems. Explain STRIDE as the classical checklist. Then the AI-specific attacks: prompt injection, where hidden instructions in anything the model reads become instructions it follows; memory and context poisoning, which is why provenance on retrieved context is a security control and not just data hygiene — memory without provenance becomes accumulated hallucination; goal hijacking across multi-step sessions; unsafe tool use; inter-agent trust escalation. One number: MCP became the standard way to connect models to tools and drew 99 published CVEs in 2025 — and he runs MCP servers. Close the section with the three questions a PM asks in a design review: what does this agent read that an outsider can write to, what can it do that we could not undo, and what would we see if it were doing something wrong right now.

Close on the governing principle: the common mistake is not under-engineering, it is over-engineering — building multi-agent coordination before the permission system works.

Warm, direct, concrete, unhurried. No hype.
